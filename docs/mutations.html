Breaking the line is the easy half

apolisp’s fifth verification rung is a shell script that damages its own source on purpose, forty-five times, and checks that a named test notices each time. Everything else it does is the other half of the job: telling a mutant the suite caught apart from a mutation that never happened. From outside they are identical, and the wrong reading is the flattering one.

just mutate/45 mutations/3 files/6 test targets/ADR-055

killedThe mutation applied, built, and the named test failed. The only outcome that means the check works.
SURVIVEDThe mutation applied and the suite stayed green. A hole.
survived, as declaredPredicted in advance, with a written reason.
DECLARED SURVIVOR DIEDAlso reported. The reason it could not flip has stopped being true.
PROVES NOTHINGThree ways: the pattern no longer matches, the mutant does not build, or it never finished.
DUPLICATE DESCRIPTIONTwo checks calling themselves the same thing. That is how a dead one hides behind a live one.
The rung

Rungs 1 to 4 ask whether the code is right. This one asks whether we would know if it were not

The oracle is a ladder: cargo check, a smoke script, a golden corpus with one snapshot per compilation phase, and a test suite written in the language itself. Rung 5 is just mutate, and it does not test the VM. It tests the other four rungs.

It is a hand-written list rather than a framework, and ADR-055 is blunt about why:

Every general mutation tool answers “what fraction of mutants die”, which is a number nobody acts on. What has actually paid here, eight milestones running, is a handful of mutations chosen because someone believed a specific line was load-bearing. The value is in the choosing; automating the choosing removes it.

It is also deliberately outside just verify. Every mutation is a full rebuild, so a run is minutes rather than seconds, and a gate that slow is a gate people learn to skip — which is worse than no gate, because a skipped gate still reads as coverage. Run it when touching something a check is supposed to hold.

The unit

One mutation is six arguments

There is no DSL and no config file. Every entry is a call to one shell function, and the entry is the documentation of what the line was believed to be holding.

mutation src/lib.rs \
  'string(&a[0], "str-scalar-len")?.chars().count() as i64' \
  'string(&a[0], "str-scalar-len")?.len() as i64' \
  "$LANG" \
  'str-scalar-len counts scalars, not bytes — the whole of ADR-049'
1
file
One of three: the VM, the prelude written in the language, or a corpus program.
2
old
The exact text to break. It must occur exactly once — zero matches and two matches are both errors.
3
new
What to put there. A plausible wrong implementation, not a syntax error.
4
check
The cargo test selector that is supposed to catch it. Naming one test rather than running the suite is the point: the claim is about a specific check.
5
desc
The behaviour the line carries, in a sentence. Printed as the heading and checked for duplicates.
6
survive
Optional. Present means “this one should not flip”, and its value is the reason.

Substitution is done by an inlined Python snippet rather than sed or perl -0pi, because it counts the matches first and refuses on anything but one. That is not fussiness; it is the finding from milestone 9, below.

The verdict · the shape of the whole script

Three gates, and the names they print

A mutation run has one desired outcome and five ways of failing to produce it, and four of the five look like success if nobody is checking. So each is asserted separately, in order, and each one prints a different word.

  1. 0

    Is this description already taken?

    Checked before anything is touched. A sibling project found a dead check hiding behind a live one under a shared description — the run reported a pass, and the pass belonged to the other check.

    !! DUPLICATE DESCRIPTION another check already calls itself this
  2. 1

    Did the edit change the file?

    A pattern that no longer matches leaves the tree untouched and the suite green. That is indistinguishable from a survivor, and reads as the flattering one.

    !! PROVES NOTHING the pattern no longer matches
  3. 2

    Did it finish inside 120 seconds?

    A mutant can hang rather than fail. Milestone 8 has one that stops decrementing fuel and terminated only because a step counter happened to carry a guard. The bound is a perl fork with an alarm, so “it never finished” is its own outcome rather than a hung terminal.

    !! PROVES NOTHING the mutant did not finish inside 120s
  4. 3

    Did the mutant build?

    A mutant that does not compile runs no test at all. Detected by matching could not compile and error[E….] — not a bare ^error:, because cargo prints error: test failed for exactly the outcome this script wants. The first run of the harness reported all eight of its mutants as broken builds for that reason.

    !! PROVES NOTHING the mutant does not build, so no test ran
  5. 4

    Did the named test fail?

    From the exit status, never from grepping output for a word. A sibling project took the verdict from a grep plus an unconditional “a FAIL above is expected” message, and had twenty of its eighty-two checks go quiet without it showing.

    The answer forks against argument six.

    killed failed, and no survival was declared
    survived, as declared passed, and a reason was written in advance
    !! SURVIVED passed, and nothing predicted that
    !! DECLARED SURVIVOR DIED failed, so the declared reason has stopped being true

The script exits non-zero if any entry landed anywhere except killed or survived, as declared, and prints the offenders under the heading “checks that proved nothing” — which is the phrase the whole design is organised around.

Where gate 1 came from

Milestone 9 ran twelve mutations through perl -0pi with a pattern containing \\n, meaning to match the literal backslash-n inside a Rust string. Under single quotes the shell passed it through unchanged, so perl saw a regex matching two backslashes where the file has one. Two substitutions never fired. Both runs reported a green suite, which is precisely what a surviving mutant reports.

It was caught only because one of the two had been predicted to survive for a specific reason, and checking that reason meant opening the file. Every note in docs/notes/ written before that pass used unchecked substitutions, and its survivor counts should be read with that in mind.

Argument six

A survivor written down in advance is evidence; the same survivor found afterwards is a discovery

Two kinds of survivor are legitimate, and neither is a hole. The first is a claim no test can separate — a performance claim is the recorded example. The second is a guard against a failure so severe that it is enforced twice on purpose.

The one declared survivor in the tree is the second kind. str-scalar-slice guards from <= to, and the guard is unreachable while the scan’s early break stands, so deleting it changes nothing observable:

mutation src/lib.rs \
  '(Some(f), Some(t)) if f <= t =>' \
  '(Some(f), Some(t)) if true =>' \
  "$LANG" \
  'str-scalar-slice: the f<=t guard, without which a backwards slice panics' \
  'the scan breaks at `to`, so with `from > to` it never finds `from` and the
   missing-bound error fires first. The guard is unreachable while the break
   stands, and both exist because reaching `s[f..t]` backwards is a panic where
   ADR-039 requires a throw — a process abort is worth enforcing twice.'

Declaring is not excusing. A declared survivor that starts dying is reported as loudly as an undeclared one that lives, because a mutation that now flips means the reason it could not has stopped being true — the break moved, or someone reached the branch another way.

And the declaration has to be written before the run. Milestones 4, 7 and 8 each predicted every survivor they got, which is the only reason those passes count as results rather than as fishing.

The working tree

For the length of a run, the checkout is a mutant

The script edits src/ in place and restores after each mutation. That is the cheapest thing that works, and it has three consequences the script has to handle rather than document.

A lock, because two runs would restore each other’s mutations

An mkdir lock under $TMPDIR. A second mutate.sh would produce nothing trustworthy — every result noise. A just verify started alongside a run failed once and looked like a real regression until the timing was noticed.

One trap handler, not two

Restoring the files and removing the lock are combined into a single trap, because a second trap on the same signals replaces the first rather than adding to it. Set separately, whichever came last would run and the other would silently never fire.

File copies, not git stash

The originals are copied to /tmp and restored from there. The stash stack is repo-global and shared across worktrees, so a pop can retrieve somebody else’s entry.

The procedural scar

Milestone 2’s fix was written while a mutant was still applied, and the git checkout that reverted the mutant reverted the fix along with it. Mutate against a clean tree, always.

The grouping is the script’s own section comments, and it reads as a history of the project rather than a map of it: the set grew a milestone at a time, each pass seeding the mutations its notes had already run by hand. It is not complete, and the gaps are the honest kind — milestones 6, 7 and 10 ran their passes and live only in docs/notes/, so nothing re-runs them.

Adding one

The routine, which is four steps and one rule

  • Pick a line you believe is load-bearing, and say what it carries in a sentence. If the sentence is hard to write, the mutation is not aimed at anything.
  • Write the prediction down first — caught or survived, and why. Two lines in a commit message is enough. The refutations are the interesting part, and a prediction filled in afterwards always reads as a discovery.
  • Name the single test that should catch it, not the whole suite. Milestone 7 is the reason this matters: the in-language suite is the only rung that catches a semantic mutation, and an invariant no program can observe needs a Rust test instead. A mutation that dies to the wrong rung is worth knowing about.
  • Run it against a clean tree, and record whether the prediction held in docs/notes/milestone-N-mutants.md.

The rule is that a survivor is not fixed by adding an assertion about the mutant. Four of the nine recorded passes found a hole in the corpus rather than a defect in the code, and those were closed by adding programs. One was closed by deleting a redundant enforcement, and one by removing the way to write the bug at all — milestone 4’s fifth mutation cannot be expressed any more, because frames are released in exactly one place now, and that is the finding rather than an omission.

What it caught the day it was written

A mutation making vec-slice return a list instead of a vector survived the entire suite, including three assertions written the day before whose comment claimed “a list in, a vector out — the conversion is the point”. = crosses representations here, so (is= [1 2] …) is equally true of a list and could not see the thing it said it was checking. Fixed by asserting through str, which prints [1 2] for a vector and (1 2) for a list.

A correct assertion about the wrong subject. Nothing else in the loop asks that question.

apolisp is a personal project with one user and no stability promise. mutate.sh sits outside the line budget as tooling; the decision behind it is ADR-055, and the numbers on this page are read out of the script rather than from a run. Its three assertions were all learned from a sibling project that had twenty of eighty-two checks quietly stop checking anything.
