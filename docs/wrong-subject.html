Review reads the assertion. Nothing reads the subject.

Two properties swept every program in the corpus and were green for three days while checking bytecode the VM never runs. That is the second corpus-wide property in this project to have been dead, and the sixth check to have been green while testing the wrong thing — and not one of the six contained a wrong assertion.

Mutation Finds a check that asserts too little about what it sees. Needs the code to exist and a hypothesis about how it might break.
An unlike input Finds a check that sees too few things. Needs an input that exercises a path the existing ones do not — and needs someone to write it.

The incident

Not a weakened check — an absent one

tests/compile.rs has a helper, compile_ok, that reads a source string and compiles it. It does not expand macros. That is exactly the right shape for the hand-written snippets that fill most of the file: they are core forms, and routing them through the expander would test the expander instead of the compiler.

Two properties used the same helper to sweep every file in tests/corpus:

every_instruction_has_an_origin
slot_operands_stay_inside_the_frame

Since milestone 5 those files contain macros. So from 6c4785f onward, both properties were compiling forms that no longer resembled what the compiler is handed at run time — and asserting over the bytecode that came out.

The distinction that matters is not that the checks got weaker. The bytecode being asserted over was produced from pre-expansion source, so nothing about post-expansion codegen was covered by either property, for any program, ever. Every instruction the VM actually runs was outside the reach of both.

Why nothing noticed

The trigger and the thing that should have fired it arrived in the same commit

macros.xs entered the corpus in the commit that made expansion exist. It did not fire, because every template in it expands to something the compiler also accepts unexpanded:

(defmacro when  [test & body] `(if ~test (do ~@body) nil))
(defmacro twice [e]           `(let [v# ~e] (+ v# v#)))
(defmacro pair  [a b]         `[~a ~b])

Unexpanded, `(if ~test …) is a list whose head is if and whose members are (unquote test) — odd, but structurally a form the compiler will lower without complaint. twice puts a vector in binding position, but it is a literal vector and survives syntax-quote as one.

Breaking it needs an unquote standing exactly where a parameter vector goes, and one macro in the project does that:

(defmacro defn [name params & body]
  `(def ~name (fn ~name ~params ~@body)))

unexpanded, ~params is (unquote params) — a list, not a vector
`fn` takes a parameter vector, not a list

editor.xs is the first corpus program to define its own defn. It failed on the first run after being added.

“Holds over the whole corpus” is a claim whose strength is set by the corpus’s diversity, and nine programs that each pin one small feature are not diverse merely by being nine.

The editor is 270 lines against 212 for the other nine combined, and it broke something on the way in. That is the argument for corpus growth stated as a measurement rather than as a preference: the tenth program found what nine had been unable to, not because it was better written but because it was unlike them.

The shape

A green test is a claim about a pair

Six checks in this project have now been green while testing the wrong thing. Reading them together, the striking thing is what they have in common — and it is not carelessness.

The assertion

What the check claims. Written deliberately, read in review, and in all six cases correct.

The subject

The thing the assertion was applied to. Established by a helper, a fixture, or a default several call sites away — and read by nobody.

Every one of the six was a true assertion about the wrong subject. Not one was a wrong assertion. The bounds checks above were correct, applied to bytecode the VM never runs. A pin’s assertions were correct, at a window height where the clamp they were written for cannot fire. “Every dependency is optional” is correct, and vacuous over an empty list. A compile check compiled exactly what it claimed to compile, and compiling is not what catches an unbound global in a language that resolves them at call time.

Review reads the assertion. Nothing reads the subject.

That is why all six survived being written and read by someone who understood them. Reviewing a test means reading what it asserts; the subject is upstream, usually in a helper whose name says it does the right thing, and it changes without the assertion changing at all.

1

Milestone 1’s span property — found by mutation

Checking arity and nothing else. Two of three mutants — every origin Unknown, every span starting at byte 0 — passed the entire suite. Told in full in chapter one.

2

The two corpus sweeps — found by an unlike input

All post-expansion codegen, for every program, since milestone 5. The incident above.

3

str-scalar-slice’s from > to branch — found by mutation

Would have hidden nothing, and that was the finding. Below.

4

The editor’s two-row pin — found by mutation

Would have hidden the max2 1 clamp — the entire bug the fix was written for. The pin stopped exercising the clamp once the key hint gave up its row, and went on passing.

5

the_language_carries_no_dependencies — found by asking what it observed

Would have hidden every dependency, if the manifest were ever reformatted. Below.

6

The editor shell’s compile check — found by mutation

Would have hidden a shell calling a core function that no longer exists. Globals resolve at call time, so the shell compiled perfectly with a call to the deleted scalars-take sitting in it. Found by putting one there on purpose, not by reading it. The check now evaluates the join instead, minus the one call that needs a terminal.

Four of the six were caught by mutation, one by an unlike input, one by printing what the check observed. That distribution is an artefact of which habits were being practised, not a ranking — and the three channels find genuinely different things.

How a subject drifts: the ground moves under a check that never changed

Instances 2 and 4 share a mechanism sharp enough that the mutation ADR names it as a distinct kind: a correct check that stops covering its subject when a later change moves the ground under it. Three arrived in a single day. The two-row pin stopped exercising its clamp once the key hint gave up its row. Two more pins silently began testing soft wrap instead of clipping, on the day soft wrap became the default.

Each was still passing, still correct, and no longer about anything. Nobody edited them; the default they assumed moved, and an assumption that is never written down cannot be invalidated when it stops holding.

The mitigation, which is narrow on purpose

A pin states the mode it assumes. A pin that does not is one that stops pinning the moment the default moves — and it will keep reporting a pass while it does.

The channels

Mutation could not have found the one this page is about

The two dead corpus sweeps were not found by mutation, and no mutation would have found them. The code was not wrong. compile_ok does exactly what its name says, and every assertion in both properties was correct.

The defect was in the reach of the property, and reach is invisible to mutation of the code under test. Break any line the property covers and the property still fails, correctly, on the subject it was looking at. It only becomes visible when the input set grows a member that exercises a path the others do not.

They are complements rather than substitutes, and the failure mode of treating them as substitutes is specific: a project that mutates diligently and never adds an unlike input will keep a suite of properties that are individually sharp and collectively blind, and every mutation run will report that they are fine. That is not a hypothetical — it is three days of this project.

The cheapest one

Ask the check to show its working, before it has ever been green

Instance 5 was found by neither of the other two, and it is the only one of the six that was caught before it went wrong.

the_language_carries_no_dependencies reads Cargo.toml, splits out the [dependencies] section by hand, and asserts that every entry it finds is optional — which is the property that matters, since ADR-013 makes features host capability only, so a non-optional dependency is by definition one the language carries.

The assertion is correct. It is also vacuously true over an empty list, and the hand-rolled parse goes empty the moment anyone rewrites the manifest in [dependencies.crossterm] table style — a reformat, not a change of substance. Nothing about that would have failed.

What surfaced it was printing what the parse actually saw before trusting the assertion built on it: two dependency lines, which is the number that makes the check mean something. That number is now an assertion of its own, with a message saying the manifest format changed and this test stopped looking at anything.

Why this is the one to reach for first

Mutation needs the code to exist and a hypothesis about how it might break. An unlike input needs the input, and someone to think of it. Asking a check to show its working needs a println and thirty seconds — and it is the only one of the three that works before a test has ever been green for the wrong reason.

An empty subject is the easiest failure to have and the hardest to see, because every assertion over it passes and none of them is false. A check that observed nothing and a check that observed everything print the same verdict, and only one of them is a test.

Instance 3

A survivor is a question about which of two things is wrong

The reflex reading of a surviving mutant is “the test is too weak”. Instance 3 is the one that does not fit, and it is worth keeping for that.

str-scalar-slice had a from > to branch of its own. Removing it changed no behaviour any test could see: the scan reaches the same error either way, and ADR-039 clause 3 makes the message prose rather than contract. The correct reading was not “the test is too weak” but “the code is redundant”, and deleting it was the fix.

Then deleting it exposed something a stronger test would never have found. Without the loop’s early break, s[f..t] runs backwards and panics — a process abort, where ADR-039 requires a throw. That is now held by an f <= t guard rather than by an argument about loop ordering, and it is the harness’s one declared survivor: kept deliberately, unreachable while the break stands, and reported loudly if it ever starts dying.

What the reflex would have cost

Answering “the test” by reflex would have added an assertion, kept a redundant branch, and left the panic in place behind an argument nobody had written down. Two mechanisms enforcing one rule means no test can say which one is working — the same finding as chapter one, arriving from the opposite direction.

The sharpest case

The comment at the line named the subject the assertion could not reach

One more, filed as an erratum rather than in the note, and it is the one that makes the thesis hardest to dismiss as inattention.

A mutation making vec-slice return a list instead of a vector survived the entire suite — including three assertions written the day before, whose comment read “a list in, a vector out — the conversion is the point”.

(is= [1 2] (vec-slice ...))   ; the assertion
; "a list in, a vector out — the conversion is the point"

ADR-041 makes = cross representations, so this is
equally true of the list it was written to refuse.

(is= "[1 2]" (str (vec-slice ...)))  ; prints (1 2) for a list

The author knew the subject. The author wrote the subject down, at the line. The assertion still could not see it, because a language decision made two representations equal and the check was phrased in terms of that equality. The same hole covered take and drop, whose contract is also that they hand back a vector.

Found by the mutation rung one day after the tests were written, and by nothing else in the loop. If a stated intent sitting on the adjacent line does not protect a check from testing the wrong subject, no amount of reading will.

The trigger

A comment named the day this would break, and the day came

The dead assertion was not unguarded. It carried this, written at milestone 2:

Nothing in the corpus is macro-generated yet, so every instruction traces to real source text. When milestone 5 lands, Generated becomes legal here and this assertion is the thing that has to be widened deliberately.

A correct prediction, with the right trigger, sitting at the right line of code.

milestone 2The comment is written. It names the exact future change and the exact response required.
↓
milestone 5Lands the next day. Macros exist; macros.xs joins the corpus in the same commit.
↓
—Nothing happens. A comment has no mechanism to fire — it is read by whoever is already looking at the line, and after milestone 2 nobody was.

Pair it with the finding from instance 1: the decision record had already specified the fix for that dead property, in its verification clause, and the implementation had built the debug renderer and then not snapshotted it. Twice now the project has written down the thing that would have prevented a defect, in a place that was not consulted at the moment it mattered.

Which turns a comfortable belief into an open question. Documentation that anticipates a future change is doing real work only if something reads it at the moment of the change, and neither a code comment nor a decision record has any such mechanism. The candidate fix on the table is narrow: make the trigger a failing test with an #[ignore] and a reason, so it is the suite asking rather than the reader remembering.

The fix, and the fix’s own trap

Legalizing Generated nearly reintroduced instance 1

The repair is small. compile_expanded mirrors what the binary does — read, expand, compile — and both corpus sweeps use it. The prelude deliberately stays out: folding it in would leave the span assertion checking prelude origins against the program’s source length.

The origin property now accepts Generated, which is the widening the comment asked for, and still refuses Unknown. And one assertion was added that at least one instruction per program traces to Source.

Why that last assertion exists

Legalizing Generated without it would let a mutant that stamped every instruction Generated pass — a property that accepts anything, which is the exact failure milestone 1 is about, reintroduced by the fix for a different one.

That is the pattern worth carrying: widening a check to accommodate a legitimate new case is the moment it is most likely to become vacuous, because the widening is written while thinking about the case that motivated it and not about the case that empties it.

The timing

The habit costs least exactly when it feels least necessary

Four of the six were caught by mutation, and none of the four took five minutes. But the number that changed how the habit is written down is a different one:

3 of 6caught the same session
3 of 6believed for days
0 of 6a wrong assertion

Three were caught in the session the check was written — before the thing had ever been trusted. The other three had been green, and believed, for days.

The habit costs least at the moment the assertion is written and most after it has been green for three days, which is exactly backwards from when it feels necessary.

A fresh check is the cheapest thing in the world to break: the code is loaded, the subject is in front of you, and no other work depends on it yet. A check that has been passing for a week has acquired the strongest possible evidence that it is fine, which is that it keeps passing — and that evidence is exactly what a check testing the wrong subject also produces.

So the project’s habits file no longer says try to break your own test. It says to do it at the moment the check is written, and it gives the three ways: mutate it, feed it an input unlike the others, or just print what it observed.

Still open

What six instances do not settle

The count is the note’s ledger at a date, not a live inventory — and this page is the wrong place to keep one, for the reason E-17 gives. Three questions the six raise and do not answer:

  • Should a corpus entry state what it reaches that no existing entry does? The .out list is already an asserted decision; coverage intent is not. “Add an unlike input” only works as a habit if unlikeness is deliberate, and the tenth program was unlike the others by accident — it was written to be used, not to be diverse.
  • Is there a cheap check that a corpus-wide property compiles through the same pipeline as the binary? Both defects here were a test helper diverging from main.rs, and that divergence is mechanically detectable in a way “is this assertion about the right thing” is not.
  • Should corpus growth be scheduled? It currently happens when a program is written for other reasons. Nine programs found nothing for three days; the tenth found it on the first run. Waiting for the tenth program to be wanted for its own sake is a detection strategy with no schedule.

None of these is decided, which is the honest place to leave it. What is decided is smaller and has evidence behind it: a check is a pair, the subject half is unread by construction, and the thirty seconds that reads it are cheapest before anyone has believed the result.
