The instrument that can lie

The last four milestones of a small Lisp VM. The habit of breaking its own tests on purpose kept working, and then changed character: it stopped finding defects and started finding holes — code that was correct and untested. Then it found something worse, which is that a mutation run can report a result that never happened.

Previously

Where this left off

apolisp is a small Lisp in the Clojure dialect with its own VM, in Rust, for one user. The binding constraint is that the core stays holdable at once — a context-window budget of about 7,000 lines — which makes a test suite that merely exists too expensive. Every test has to be doing identifiable work, and the way that gets checked is to break the code on purpose and see whether anything notices.

Chapter one ran that habit over the first three milestones and found three distinct kinds of failure. Chapter two ran it over the next three and found three more, two of which a mutation check could not have answered at all. It ended on an admission: the property the entire design exists for — that a running computation is data you can suspend, move, and resume — was still an aspiration rather than a fact.

This chapter is the remaining four milestones. The aspiration became a property, and the first thing that property did was demonstrate its own blind spot.

Round seven · milestone 7

A generational handle table, and two holes in its corpus

Milestone 7 is the host handle table: opening files, generational handles so a stale one is an error rather than a silent alias, and with-open as a macro over try/finally. Seven mutants, predictions written first. Two survived, and both were predicted. Predicting a survivor is not a win: it means the hole was visible from the armchair and the suite had it anyway.

The first one had the shape everything after it would repeat:

The read path could ignore the generation entirely

Every test stayed green. The suite checked close on a stale handle and open? on one — both of which go through a different accessor from the one every actual read and write uses.

So the aliasing bug the generation exists to catch was covered on the rare path and open on the common one. Nothing was wrong with the code. What was wrong was the belief that the corpus was checking it.

The second survivor is the more instructive, because it is a test that could not fail against the shape it was written to forbid. The error record for an I/O failure carries a :path key only when the operation names one, so a failure with no path has four keys rather than five with a nil in it. The assertion for that read:

;; the test, as written
(is (= nil (get read-failure :path)))

;; the mutation: emit `:path nil` on every fault
;; result: passes. `get` answers nil for an absent key
;; and for a key present with a nil value.

Fixed with contains?, plus a count on both shapes so the key set is pinned as a whole rather than one key at a time. This is chapter one’s dead-test pattern arriving in a language feature instead of a span invariant, which makes it a property of how assertions get written rather than of any one subsystem.

Before any of that, though, the milestone produced a design error the suite caught on its first run — and the interesting part is where it wasn’t. The plan said to pre-register what would break. I predicted the four-path cleanup matrix, because that is what the previous milestone’s finally tests exist to catch. Those passed immediately. What broke was simpler and I had it wrong in the design:

;; wrong: bump the generation when the slot is released
if e.host.take().is_some() {
    e.generation += 1;              // the id that just closed it is now stale
    self.free_handles.push(id.0);
}

Closing twice is what a correct with-open does when the body closed explicitly. Bumping at release makes the second close report the aliasing error instead of being a no-op, so idempotent close and stale detection were mutually exclusive. The bump belongs at reuse. Obvious in retrospect, invisible while writing it, and caught by a test suite written in the language itself the first time it ran.

Milestone 8

Suspend, snapshot, resume — the property arrives

The whole design rests on the Rust stack being empty at every instruction boundary — no host recursion, explicit frames, all mutable state owned by the VM — so that execution state is plain data. Milestone 8 is where that stops being a design and becomes a test: run a program to fuel exhaustion at an instruction boundary, take an image, rebuild a fresh VM from it, resume, and compare the entire transcript against an uninterrupted run.

Two forms, and the second is a different claim from the first. Cut at every instruction boundary and round-trip once, over nine programs each carrying a distinct piece of state. Then cut at every boundary and round-trip repeatedly to the end — because a field restored to a plausible default survives one trip and drifts over fifty.

One prediction from the decision record was refuted before the code was finished. Preserving structural sharing means an object can name an id it has not reached yet, so the entry said the decoder would need two passes. It does not:

;; encode children before pushing their parent, and every id
;; an object names is lower than its own. The table comes out
;; topologically ordered; the decoder is one forward loop.
fn obj(&mut self, addr: usize, build: impl FnOnce(&mut Encoder) -> Obj) -> Ref {
    if let Some(&id) = self.seen.get(&addr) { return Ref::Obj(id); }
    let o = build(self);                    // children first
    let id = self.objects.len() as u32;
    self.objects.push(o);
    ...
}

That is available only because the object graph is acyclic — and it is acyclic because the one thing that can form a cycle, a mutable cell, is an arena id rather than a pointer. A decision made three milestones earlier for a different reason paid for a simplification here. The cost clause was corrected in errata; the decision stood.

Four fields the round-trip could not see

Ten mutants against the snapshot. Four survived. The property — every instruction boundary, nine programs, two forms — caught none of them.

Four fields could be dropped from the image with the suite green

The gensym counter. The handle free list. The handle generations. The sign of a negative zero.

Every one is a field the encoding handles correctly and the corpus never populated. gensym is a primitive, so the counter is live at run time and not only during expansion — but no program in the list called it, and a resume that restarted it would reissue a name it had already handed out. The two handle fields were carried deliberately, for a scenario I reasoned about while writing them: open a file, close it, snapshot, open another. The second open reuses the freed slot under a bumped generation and that id reaches the transcript. The test used one with-open, so no slot was ever reused.

Code written because the gap was anticipated, sitting untested for exactly the reason it was written.

And negative zero, which had already bitten this project once — an earlier miscompilation had -0.0 and 0.0 sharing a constant-pool entry — was absent from the snapshot corpus. The fix computes it rather than writing the literal, and checks it through (/ 1.0 z), where the sign is the difference between ##-Inf and ##Inf. A test that merely printed z passes against an encoder that stores an f64 instead of its bits.

The general statement is now recorded next to the property itself: a round-trip property tests the encoding of whatever its corpus constructs, and nothing about what it does not. Adding state to the VM means adding a program that creates it. The property will not ask.

Milestone 7 had made this milestone’s exit condition unreachable

The snapshot rules say an image is refused while a host handle is live — adapter checkpointing is deferred, so a live resource is a refusal and not a best effort. Milestone 7 had made io/stdin and io/stdout permanent entries in the handle table.

The open-handle count was never zero, so every snapshot would be refused

Milestone 7 made milestone 8’s exit condition unreachable. Nothing failed, because nothing had yet asked.

The fix was already written down — the snapshot entry says caches and registry entries are “declared either reconstructible or excluded” — but it had been written about caches, not about handles. The two standard streams are recreated at the same ids in any build, so restoring them is restoring rather than inventing. A file is not, and never becomes one by that argument.

The shape is what generalizes. Two entries, each careful on its own, combined into a dead exit condition — and no test could report it, because the milestone that would ask had not been built yet.

Milestone 9

One chunk per session, so a closure never leaves its own

A closure names its function prototype by a bare index into the chunk it was compiled in, so a closure means nothing outside that chunk. That is fine for a file and fatal for a REPL, where every input is its own compilation and a function defined on one line has to be callable on the next. The open question proposed the general fix: a VM-owned registry of chunks, with each closure carrying a chunk id.

Reading the code changed the answer. A registry means a closure’s chunk id has to resolve after an image is restored, so the snapshot would have to serialize every chunk — instructions, constants, spans — or take a registry from its caller. The cheaper reframing removes the condition instead:

;; one chunk per session; each input appends to it
chunk.protos:
  [0] <top of input 1>
  [1] f              ← index never moves, so this stays valid
  [2] <top of input 2>
  [3] g

Existing indices never move, so no closure ever leaves its chunk and the question stops arising. The value representation, the closure representation, the dispatch loop, and the image are all untouched. The registry stays available for the thing that would actually force it, which is migrating an image to code assembled differently — and that is already out of scope.

The rest of the milestone came from one sentence: a REPL session is one compilation unit. Macros persist across inputs, the gensym counter runs monotonically to the end of the session, and the reader configuration is the session’s to change. Three subsystems, one rule. The gensym half is the load-bearing one — a counter that restarted per input could hand input 2 a name input 1 had already used, and a fresh symbol that is not fresh is the only thing gensym may not produce.

Two of the twelve mutants never ran

Twelve mutants. One real survivor — the prompt printed a thrown value but dropped its suppressed chain, so a cleanup that throws while unwinding reported the winner and lost the original, which is usually the failure worth reading.

Two of the twelve did not apply at all.

;; the substitution, under single quotes
perl -0pi -e 's/println!\("--- suppressed\\\\n\{\}"/.../'

;; the shell passes \\\\n through unchanged.
;; perl reads it as: two literal backslashes, then n.
;; The file has one. No match. Nothing edited.
;; The suite ran green — which is exactly what a
;; SURVIVING mutant looks like.
A mutation that never happened is indistinguishable from one that survived

And the wrong reading is the flattering one: “it survived” is a finding, “it never happened” is a wasted run being recorded as a finding.

Nothing about the output distinguishes the two cases. This was caught only because that particular mutant had been predicted to survive for a specific reason, and checking the reason meant opening the file. Which means the prediction discipline — kept for three chapters because a refutation teaches more than a confirmation — turned out to be load-bearing for something else entirely: it is the only reason a false result got questioned.

Every mutation note in this project before that point was produced with unchecked substitutions. Their survivor counts should be read with that caveat. The correction is recorded in place; the notes were not quietly rewritten. The rule now is that a mutation asserts the old text was present before writing the new, and it argues for a specific shape of tool: deleting a named line fails loudly when the line has moved. A pattern-matching script fails silently.

One mutant that round turned out not to be expressible at all. The function deciding whether a REPL line is incomplete takes a string and nothing else — it builds its own throwaway symbol table internally — so making it pollute the session’s table is a change to the signature rather than to a line. That is the best outcome a mutation pass can have, and it arrived by accident: the parameter had been dropped for an unrelated reason.

Milestone 10

Network error kinds, and a sort that was already sorted

The last milestone is host adapters — terminal, TCP, JSON — and it is the first that lives outside the line budget, on the principle that substantial host capability is a Rust library behind the handle table rather than a language subsystem. That principle had cost nothing while it described an empty set. The moment it describes real files it becomes a way to move lines out of a budget by moving them into a directory, so the budget test now excludes the directory and prints what it excluded, with per-file counts, on every run.

TCP is in this milestone for one reason. Three error kinds — :timeout, :would-block, :connection-reset — had been named two milestones earlier and deliberately left out, on the grounds that a kind nobody can raise is a guess with a colon in front of it. A file can produce none of them. An entry that defers three kinds and then never adds them has not been careful, it has been lucky.

The first prediction was refuted immediately. Setting a read deadline and letting it expire does not raise :timeout:

;; Rust documents a read deadline as WouldBlock *or* TimedOut,
;; by platform. Unix gives the first, Windows the second.
(tcp/set-timeout server 30)
(try (io/read server 4) (catch e (get e :kind)))
;; ⇒ :would-block on macOS. :timeout on Windows.

So :timeout’s only reliable raiser is a connect with a deadline, and a test pinning one kind would pass on the machine that wrote it and fail on the other. The test accepts both and the trap list says why.

Nine mutants, nine correct predictions, three survivors — and one of them is a different kind of finding from everything in these three chapters:

The key sort in the JSON decoder was unreachable

Deleting it left the whole suite green — not because nothing tested the order, but because the library underneath had already sorted. Its default map is a BTreeMap.

Two mechanisms enforcing one rule, which is chapter one’s finding in a new place, and it gets that finding’s answer: delete the redundancy rather than add a test. A test written to pin the order would have passed against a version with the sort removed and against one with the library’s guarantee removed, which means it would have been measuring nothing. What replaces the line is a comment naming the dependency, because the guarantee is now someone else’s — enabling one Cargo feature on that library swaps the map for an insertion-ordered one and every golden holding a decoded object moves.

The other two survivors were ordinary holes: :connection-reset could be mapped to the catch-all with everything green, which would have honoured the letter of the deferral and not the point, since it is the kind a program most wants to retry on. And a socket error could drop the address it was for, naming the failure but not the thing that failed.

This milestone also ends the project’s zero-dependency property, and it ends asymmetrically. Two dependencies, both in the adapters, both declined for the language: cargo tree --no-default-features is still an empty tree. The claim narrowed to something still mechanically checkable, which beats letting it decay into prose.

Where it ended

The build order is finished, and the property chapter two ended on is a property now: fuel suspension, an image with structural sharing preserved, resume into a fresh VM, transcripts compared with emitted effects included. The subtraction claim is also a fact rather than a feeling — the gate builds and tests three points of the feature lattice, so “cutting a host capability leaves the language alone” is something that compiles and runs rather than something the decision log asserts.

What changed across these four milestones is the character of what the instrument finds. Chapters one and two found defects: a dead test, a rule enforced twice, a corpus that could not distinguish right from plausibly wrong. This chapter found almost no defects at all. Every survivor was code that was correct and untested — a field the encoder handled properly and no program created, a path the generation check covered and nothing walked, an error kind classified correctly and never provoked.

That is a harder thing to fix, because no amount of strengthening a property addresses it. The property was strengthened — every instruction boundary, two forms, nine programs — and it still saw nothing, because a property only sees the state its inputs create. The lever is the corpus, and the only reliable way found to discover what the corpus is missing is to break the code and watch what stays green.

Which is why the milestone-9 result is the one worth carrying forward. The instrument that answers “what is my test suite not checking” can itself return a confident, well-formatted, entirely fictional answer, and nothing in the output says which. It was caught by a habit kept for an unrelated reason: writing down what should happen before running it, because a refutation teaches more than a confirmation. The prediction did not find the bug in the code. It found the bug in the method.

apolisp is a personal project with one user and no stability promise. Its decision log is append-only; corrections go in errata rather than over the original, which is how a paragraph that was reviewed, committed, and wrong gets fixed without erasing that it was believed. Every mutation pass quoted here is recorded in docs/notes/ with its predictions, its commit, and whether it was refuted — including the two that turned out not to have run.
