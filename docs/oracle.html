The tests were green and two of them were dead

Three milestones of a small Lisp VM, and four rounds of deliberately trying to break its own test suite. Each round that found something found a different kind of failure — and the round that found nothing is part of the result.

apolisp/Rust, zero dependencies/3 of 10 milestones/38 decision records

The premise

Build the oracle before the language

apolisp is a small Lisp in the Clojure dialect with its own register-ish VM, written in Rust for one user. It has no compatibility contract and no stability promise. The interesting constraint isn’t performance or features — it’s that the entire core has to be holdable at once, by one engineer and by one language model. That is a context-window budget, about 7,000 lines, and every other decision defers to it.

A budget like that changes what verification is for. You cannot afford a test suite that merely exists; you need one where each test is doing identifiable work, because the suite competes for the same attention the code does. So the build order puts the oracle first — a four-rung ladder from cargo check through a smoke script, a golden corpus with one snapshot per compilation phase, and eventually a test suite written in the language itself. The instruction in the build doc is blunt:

Write this before the reader is finished — a failing smoke test is a better queue than an empty one.

And one rule above all others: never regenerate a golden file to make a test pass. That is a failed task, not a fix.

The seed of everything below came from a sibling project. Its notes record a mutant that deleted the compiler’s line-counter restore and passed the entire suite — because every test program in its corpus had subexpressions on the same line as the enclosing form. Green corpus, dead mechanism. That went into the prior-art file as a thing to watch for, months before there was any code here to watch.

Knowing about a failure mode did not prevent it

Milestone 1 reproduced that exact failure. In the first milestone. After writing it down as a warning.

Round one · milestone 1

A test that could not fail

Milestone 1 is a reader, a printer, and source spans. Spans are the awkward part: they have to cover immediates too, so an error can point at a symbol occurrence, but a symbol is a 4-byte interned id with nowhere to hang metadata. The design puts origins in a parallel tree beside the value graph rather than inside it — one origin per syntactic child, positionally.

That structure gets a property test: every source span lies inside its file, both ends fall on character boundaries, and child-origin arity matches child count. Ten tests green, four corpus programs, everything passing.

Then, three mutants, with predictions written first.

Every leaf origin becomes Unknownpasses — the test is deadsurvived
Every span starts at byte 0passes — the test is deadsurvived

The property was checking arity only. Every span in the system could have been systematically, totally wrong and the whole suite stayed green. The one third that worked was the third that counted things.

Worse, in a way that is more useful than the bug: the decision record had already specified the fix. Its verification clause called for snapshotting the rendered origins, and the implementation had built the debug renderer and then not snapshotted it. The document was right and the code was short of it, and nothing in the loop noticed except an explicit attempt to break the test.

Fixed by adding a .spans golden per corpus program. Both surviving mutants now fail.

Round two · milestone 2

A rule enforced twice, so deleting either changed nothing

Milestone 2 is the core AST, a slot-based bytecode compiler, and a disassembler. One decision it inherits: tail calls reuse the caller’s frame, except that a call in tail position inside a try with a finally is not a tail call, because the frame is still needed to run the cleanup.

That rule got a test. It asserted both directions — a pending finally suppresses the tail call, and closing the region brings it back. Four mutants ran against the new compiler; three died as predicted. The fourth deleted the region check that the rule’s own test was written for.

The suite stayed entirely green

The rule was implemented twice. The try lowering cleared the “this is a tail position” flag before descending into a protected body, and the call site checked an open-handler-region counter before emitting a tail call. Because the flag was already false by the time any call was reached, the counter could never fire.

It read as belt-and-braces. It was dead code wearing a safety net’s clothes — and the test could not distinguish the two, because both of its assertions were true under the mutant. The other mechanism was carrying them.

The fix was deletion, not another test. The lowering now passes the flag through untouched and the counter is the single enforcement point, at the site where the decision is actually made. The mutant now fails.

No golden file changed. Removing the redundant clause produced byte-identical bytecode across the whole corpus, which is exactly what “this branch was unreachable” should look like from the outside.

So a mutation check does not only find dead tests. It finds duplicated enforcement — two mechanisms implementing one rule, with no way for the suite to say which is working. Adding a test that pinned both would have preserved the ambiguity rather than resolving it.

Round three · a fresh reader

Correct code that nobody was watching

The process doc keeps one tool in reserve: a diff-only review by a fresh context, given the change and none of the reasoning behind it, tasked only with enumerating why it is broken. Milestone 2 got one. It ran its own mutations and found seven more survivors — all of them in code that was correct, and none of it observed.

The one to remember is a single token.

;; ((f) 1)  — the operator is itself a call
;; one argument changed from `false` to `tail`:

0000  GETGLOBAL   r3 <- f
0001  TAILCALL    r3(0)      ;; returns (f)’s value. Never calls it with 1.
0002  CONST       r2 <- k0
0003  TAILCALL    r1(1)      ;; unreachable — and r1 was never written

A function that computes its own callee now returns the callee instead of calling it. Silent, total, and wrong. All 31 tests passed. Every golden file was byte-identical.

The cause was corpus shape, not test design

The tail-call test existed, asserted both directions, and was written by someone thinking carefully about the rule. It only ever exercised a call whose operator was a plain symbol — because no program in the corpus had a call whose operator was itself a call.

The corpus had been assembled to look representative. That is not the same thing as being assembled to distinguish. A program earns its place in a corpus because some plausible wrong implementation compiles it differently.

The other six were the same shape: a decision with a home in the decision log and no test, so the log read as enforced when only the code was carrying it. Sequential let bindings could become letrec. The scope walk could resolve outward-in instead of inward-out. A function’s own name could beat its parameters, so (fn f [f] f) returned the function instead of its argument. All green, every time.

The same review found a stack overflow the suite could never have caught, because it wasn’t a wrong answer — it was a killed process. The compiler aborted with SIGABRT at around 1,400 levels of nesting, on input the reader happily accepted at 3,000. That became a bounded nesting depth, checked once, in the reader — the only place that needs it, since every later phase recurses at most once per level of form nesting. Checking again downstream would have been the duplicated enforcement the previous round had just finished deleting.

Round four · milestone 3

Reporting the null result

Milestone 3 is the VM: an explicit frame stack, closures, proper tail calls, and enough primitives to run something. Seven mutants against its load-bearing lines, predictions written first.

Worth two lines rather than none. The interesting result is the refutation, and “no refutation” only means anything if the predictions were written down before the run.

One of those seven has history. The sixth is a bug that genuinely shipped into the working tree during this milestone, and it was found by a program crashing rather than by a test.

Returning from a call restored the wrong slot-stack length: it truncated to the callee’s base instead of the caller’s saved length. A caller’s frame extends well above its call window — the window is allocated early and the caller keeps using slots after the call returns — so the next high slot write blew up with an index out of bounds, three subsystems away from the cause.

The fix was small. The useful part was turning the bug into a mutant afterwards and checking that the fix is observed and not merely present. It now fails two tests, so the same slip cannot come back quietly.

Milestone 3’s exit condition got the same treatment. “A tail loop runs in constant space” is not observable from outside the VM at all — a loop that quietly grew the frame stack still prints the right answer — so the VM reports its high-water marks and the test compares a hundred thousand iterations against ten. Both numbers, frames and slots. Frames alone would have passed an implementation that reused frames and leaked slots, which is exactly what the sibling project measured when it found that tail-call optimization fixed its stack and not its heap.

What it adds up to

Four rounds, three kinds of failure

The four passes did not find four instances of one problem. They found three distinct failure modes, and the progression is the actual result:

  • A dead test. The assertion ran and could not fail. Classic, well-known, and still the first thing found here.
  • Duplicated enforcement. Two mechanisms implementing one rule, so the suite could not attribute the behaviour to either. No test can find this, because every test passes. The fix is deletion.
  • An undistinguishing corpus. The test was right, the code was right, and the input space never separated the correct implementation from a plausible wrong one.

Only the first is what “mutation testing” usually means. The second and third are questions about the shape of the verification apparatus, and nothing else in this loop asks them — not the property tests, not the golden corpus, not a careful review by the person who wrote the code.

The honest caveat

Self-run mutation found one survivor in milestone 2. A fresh context, given the same diff and none of the reasoning, found seven more in the same code an hour later. Running mutants on your own work is worth doing and is not a substitute for someone who does not already know what the code is supposed to do.

The cost is low enough to be uninteresting: change a line, run the suite, restore. Ten minutes a milestone. The discipline is entirely in writing the prediction down first, which is what separates a result from a fishing expedition — and which is why the null result in round four is reportable at all.

There is one procedural scar. Round two’s fix was written while a mutant was still applied, and the git checkout that reverted the mutant reverted the fix along with it. Mutate against a clean tree, always.

Where it stands

The reader, the compiler, and the VM all work. A recursive function runs; a hundred thousand tail calls run in constant space; the smoke script reaches every stage but macro expansion, which is milestone 5 and is supposed to be red.

The twelve errata are their own small argument for keeping a decision log that can be corrected rather than edited. Two of them came from building rather than reviewing, and both were code sketches inside decision records: a predicted 24-byte value type measured at 16, and a data structure whose sketch could not be implemented as written alongside its own prose. The prose survived two reviews; the code blocks did not survive first contact.

What is not yet proven is the thing the whole design is for. This VM keeps its entire execution state in plain data — an explicit frame stack, flat slots, arena-indexed cells — so that a running computation can be suspended, serialized, moved, and resumed. That claim gets its oracle at milestone 8: run to fuel exhaustion, snapshot, resume in a fresh VM, and compare the full transcript against an uninterrupted run, effects included.

Until that test exists, the most important property in the project is an aspiration rather than a fact. Which is, more or less, the point of everything above.
