Nobody had written a program in it

Ten milestones produced a working machine and a suite of a hundred tests that had stopped being able to say anything new about it. The gaps were all one layer up, in the part a test suite structurally cannot see — and finding them took an afternoon of ordinary programs rather than another property.

apolisp/Rust; zero dependencies in the language/build order complete/50 decision records

Where this left off

Chapter one broke its own tests over the first three milestones and found three kinds of failure. Chapter two did it over the next three and found three more. Chapter three finished the build order, and found that the instrument doing the finding can report a result that never happened: a mutation whose pattern no longer matched left the tree untouched, the suite green, and a run indistinguishable from a surviving mutant.

That is where the queue ran out. Ten of ten milestones done, forty-five decision records, and nothing in any document saying what the project was for past that point. This chapter is what happened next, which was mostly not what the plan would have been.

Verification

A gate that found nothing

Everything had been verified on one machine, on one operating system. The follow-up had been filed for a while: run the same gate on Linux, because a platform assumption baked into a golden or an error classification is invisible on the machine that wrote it.

The prediction, written down first, was that socket error classification would be where the two platforms parted. It is the newest code, and the trap file already records one platform split there. It was refuted immediately — green on the first run, no source change, and a direct probe gives the same answer on both:

;; the same program, macOS and Linux
read-deadline: :would-block
reset: :connection-reset after 2 writes

Which turns out to say something the green run did not. The test for that deadline accepts either of two error kinds, because the language documents one on Unix and another on Windows. Both Unixes agree, so that tolerance is carrying Windows alone — and no run has ever taken the branch that needs it. A test written to be robust across three platforms has been exercised on two, and the third is the one it was written for.

The negative result is the result

108 tests, three points of the feature lattice, two operating systems, no diff. What that buys is not confidence that the code is portable — it is knowing which tolerance in the suite is currently untested, and why.

The soak

A mutant that reached the source and not the binary

The verification ladder had ended merge → soak → tag since the beginning, and the soak had never run. It was three words in a document: leak checks, reader fuzzing, release-build divergence. Written out, it is a script and a container stage.

The reader fuzzer is the ordinary half. Two generators — token soup, and character-level mutation of real corpus programs — and three claims: the reader never panics, whatever it accepts round-trips with well-formed origins, and whatever it rejects renders. The third is free, because rendering an error whose span falls outside the source or off a character boundary panics rather than returning a wrong answer.

Two checks on the fuzzer itself, both of which mattered. Counting how many generated inputs parse: token soup 13%, corpus mutation 68%. Without that the accept-side oracles could have been firing on almost nothing. Then reintroducing a real bug the reader’s own comment warns about — recovering a multi-byte escape’s span by subtracting a byte count — which it caught in 246 inputs and, because the harness catches panics on purpose, named the input that did it.

The leak check is where it got interesting. Nothing written in this language can leak, so the tool had to be validated by mutation instead: inject 150,000 definite leaks into a hot path and watch valgrind find them.

It found nothing. Exit zero, definitely lost: 0 bytes in 0 blocks. The mutation was in the source — grep confirmed it — and the build had recompiled. The heap summary is the tell:

total heap usage: 1,482,053 allocs, 1,482,052 frees, 127,622,370 bytes allocated

Allocations and frees differ by one, the single block the runtime holds at exit. The 150,000 boxes were never allocated at all. A Box that is allocated, never read and never freed is unobservable, and the optimizer is entitled to delete it. Wrapped in a barrier that forces the allocation to count, the same mutant was caught instantly: 149,999 blocks, exactly.

A second way to get chapter three’s wrong answer, which chapter three’s rule does not catch

Chapter three’s finding was a mutation that never applied, and its rule was: assert the old text was present before writing the new. That rule passes here. The mutation was real in the source and absent from the machine code.

The vulnerable shape is a mutant that adds work with no observable effect — a dead store, an unused allocation, a pure call whose result is dropped. One that changes an observable result is safe, which is why the earlier passes were mostly safe by luck rather than by rule. And anything mutated under an optimizing build is exposed, which is where the soak lives.

The check that caught it generalizes: read the counters, not the verdict. Total heap usage distinguishes “nothing leaked” from “nothing happened”, and every tool has an equivalent — an instruction count, a transcript, a timing. A verdict alone cannot tell the two apart, and the flattering reading is still the wrong one.

The pivot

Nobody had written a program in it

The ethos names three target workloads. After ten milestones, nothing had been written in any of them. Everything the language had ever run was a test of the language.

So: two programs. Conway’s Life on a wrapping board, and a request/response round trip over TCP with a JSON body. Both correct on the first run, which is the first result — nothing was missing that stops a real program being written.

What was missing was the layer above. Six of Life’s seventeen definitions were standard library rebuilt by hand, and five of those existed only because there was no looping form. But two findings were not ergonomics at all.

The first: a framed read looked correct and was not. The header said 27 bytes, the code asked for 42 and got 27, because a socket read returns as soon as any bytes arrive. It would have failed the first time a payload crossed a packet boundary. The second is sharper:

;; the only way to turn a string into a number
(+ 1 (json/decode "27"))   ;; => 28

There was no string-to-number conversion in the language. Not an awkward one — none. The primitive table went value-to-string and never back, so a length header, a config value, and a line of user input were all unreachable. The one path that worked ran through the JSON adapter, which is optional: building without it removed the language’s only way to read a number out of text.

A decision record from early on says features gate host capability and never language semantics. That had quietly stopped being true — not because a feature gated a semantic, but because a semantic had no home and was squatting in a feature. And the harness built to catch this could not:

The subtraction harness proves a capability can be removed. It cannot notice a semantic went missing with it

The build without JSON was green throughout, and always would have been, because nothing in the suite parses a number from a string either. The harness compares a build against a test suite, and the suite shares the blind spot.

Ten milestones did not notice, and the reason is structural rather than careless. A suite that exercises a virtual machine builds its numbers as literals. It never needs to parse one.

Q5

A macro that was complete, and still the wrong answer

The looping form had been deferred for nine milestones behind a rule: attempt it as a macro first, and admit a core form only on evidence from a real attempt.

The macro is eight lines and there is no tree walk in it. loop names its function; recur expands to a call to that name. Not walking the body is what keeps it short — and nesting then falls out of lexical scope for free, which is the real language’s rule arrived at by not implementing it.

It works. 200,000 iterations in constant space, arity checked, cleanup semantics correct. It fails on diagnostics, and only on diagnostics: errors name an identifier the user never wrote, a non-tail recur is silently accepted and grows the stack, and a user binding of that name is captured without a word.

All three have one fix — have loop walk its body — and that fix is the argument against it. The walk has to know which positions are tail positions, which is what the compiler already is. Writing it again in the prelude puts one definition in two places, in two languages, with no test that they agree, and the drift shows up as a recur the macro accepted and the compiler did not make a tail call: a silent stack leak in the construct people reach for to avoid one.

So, a core form. And the implementation made the feared duplication unnecessary rather than merely acceptable: a loop lowers to an immediate call to an anonymous function, so recur is a tail call to it, and “tail position for recur” is the flag the compiler already threads for every other tail call. The refusals read that decision; they do not make one.

One divergence from the dialect it borrows from, and it falls out rather than being chosen. A recur from a catch is allowed here, because this machine pops a handler record when it dispatches — so by the time a catch body runs there is no region to leave, and the ordinary tail-call rule permits it. Add a finally and there is an open region, and the same rule refuses it. No case analysis anywhere; the difference comes out of a counter that already existed.

Q29

A cost that was avoidable rather than payable

The next gap was the sequence library, and it had been blocked for four milestones by a real cost. Prelude functions have to be compiled into every program’s chunk; the prelude’s bytecode would then land in every disassembly golden in the corpus and grow with the prelude forever.

That had been argued about and never measured. Measured, it is worse than the argument suggested: four sequence functions are nine protos and 160 lines of disassembly, which across nine corpus programs is +1,440 golden lines — 672 to 2,112, a 3.1× blow-up for four functions.

And it is entirely a consequence of ordering. Compile the unit first and append the prelude after, and a program’s proto indices depend on the program alone:

;; six functions added to the prelude
$ git status --short tests/corpus/
;; (nothing)

The prelude’s top level becomes its own proto, run before the program’s, so no prelude instruction appears in any program’s entry point or expansion golden either. A session orders it first instead of last, because a prompt’s inputs keep appending and “last” is not a place there — so the record is a span rather than a boundary, which can say both.

It has now held three times under real changes: six functions, then three more, then six more, and the nine corpus goldens have not moved once. The prelude gets a golden of its own, because otherwise it would be the only code in the language pinned nowhere — compiled into every program and printed in none of them.

The report program

The language refuses the ambiguous spelling, then ships one

With iteration and sequences in place, the next program was chosen to not be shaped by what the language has: read a CSV, total by name, print a report sorted by total. The most ordinary program there is.

It works. The accounting is the finding — 54 lines of code, of which 30 are standard library the program has to define before it can start. The ratio had moved since Life, but less than it looked: what the previous two entries removed was iteration boilerplate, and what that exposed underneath was a different layer.

And underneath it was a trap. Strings are deliberately not sequences here, and the surface is emphatic about it: slicing raises when a cut lands inside a character, and count on a string is refused outright — with an error that tells you to name the unit. It then pointed at a length function whose name does not name its unit:

str-len "dave"  ;; 4
str-len "josé"  ;; 5 — four characters

;; so the padding idiom every report writes:
dave        |
josé       |
The one place the argument was quiet was the one place it mattered

One space short, one row misaligned, no error and nothing to notice. The refusal of count exists because this is where Unicode assumptions get made by accident. The length function was the hole in its own argument.

The fix is naming, and the reason it is naming rather than a blanket rule about byte offsets is worth keeping:

An ambiguous unit is dangerous when it flows into arithmetic and safe when it flows into an operation that validates. A byte index from a substring search can only be spent on a slice, which raises rather than guessing when a bound splits a character — so a unit mistake announces itself on the first non-ASCII input. A length is spent on subtraction, and arithmetic checks nothing.

Which also disposes of the friendly-looking option. Redefining the length function to count characters would be worse, not better: its result would stop being a legal slice bound, so the obvious full-string slice would work on ASCII and silently truncate on everything else — trading a visible misalignment for invisible data loss.

Ordering

Twenty-one lines

The rest of what the report program had to define was sorting, and sorting needed something first. The comparison operators are numbers only, so there was no way to order two strings at all — and a sort that cannot order a list of names is not a sort anybody wanted.

So an ordering that stops where it runs out: within numbers, within strings, and a refusal by name for everything else. Not a total order over every value, because ordering a keyword against a vector is a ruling nothing needs and everything would then be stuck with. Strings order by code point, which is an order and not a collation — no locale is consulted, and that is a limit to know rather than a bug to file.

The sort is a merge sort, and that is the decision rather than the detail. The version everyone writes first — take the smallest, remove it with a filter, repeat — removes every element equal to the smallest rather than one of them, so it silently drops ties. It is wrong on the first input with a duplicate and looks right on every input without one.

The same program, three times:

54lines — 30 of them library
41after the string pass — 19 library
21after ordering — none

One item on the list was deliberately not built. Calling a function with a computed argument list needs an argument count that is not known until run time, and this machine fixes both the count in the instruction and the frame’s slot count at compile time — so there is nowhere for a runtime-length argument list to go. Supporting it means a frame that grows after it is created, which reaches the slot model and the image that serializes frames, and the image is the part of this system least worth disturbing for a convenience.

But the disqualifying reason is smaller than the technical one. Nothing asked for it. It appeared in a capability probe — a list of names checked for boundness — and not in any program, while every other piece built this week was scoped by a program that had already wanted it. It is filed with the measurement and a rule for revisiting it: build it when a program wants it, and check first whether that program wants dynamic arity or only a fold.

What changed

The character of the finding has changed in every chapter, and this is the largest change yet. Chapters one and two found defects. Chapter three found holes — code that was correct and untested. This chapter found that the suite had stopped being a source of information about the language at all.

Not through neglect. 115 tests pass, on two operating systems, across three points of the feature lattice, with a fuzzer and a soak behind them. They exercise the virtual machine, which is what they were built to do and what nine of the ten milestones were about. A suite shaped that way calls primitives directly and never needs a sequence function twice, never parses a number from a string, and never pads a column — so it cannot see that any of those are missing or wrong. The subtraction harness inherits the blind spot exactly, because it compares a build against that suite.

Every gap in this chapter was found by writing a program, and none of them was on any list. The two that mattered most were not missing features but a semantic squatting in an optional adapter and a function whose name did not say its unit — neither of which a stronger property would have surfaced, because both were correct under every test that existed.

The instrument for “what is my suite not checking” is still mutation, and it acquired a second failure mode here to go with chapter three’s: a mutation can be real in the source, survive the build, and never reach the machine code. Both failures are silent, both produce a confident and entirely fictional finding, and both were caught by the same habit — writing down what should happen before running it, then noticing that it did not.

The instrument for “what is my language not doing” turns out to be simpler and was available the whole time. Write a program in it. The build order took ten milestones and produced a machine that works; an afternoon of ordinary programs produced five decision records, every one of them scoped by a program that had already wanted it.
