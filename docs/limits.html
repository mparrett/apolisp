What a mutation check cannot find

Three more milestones of a small Lisp VM. The habit from last time — break your own tests on purpose, predictions written first — kept paying, and kept running into its own edges. Each round found something the previous round’s instrument was structurally unable to see.

Previously

The instrument, and what it was for

apolisp is a small Lisp in the Clojure dialect with its own VM, in Rust, for one user. The binding constraint is that the whole core stays holdable at once — a context-window budget of about 7,000 lines — which makes a test suite that merely exists too expensive. Every test has to be doing identifiable work.

So each milestone ends the same way: pick the handful of lines the milestone actually rests on, write down what should happen if each one is broken, break it, run the suite, restore. Ten minutes. The first three milestones found three distinct kinds of failure that way — a test that could not fail, a rule enforced twice so neither mechanism could be attributed, and a corpus that never distinguished a correct implementation from a plausible wrong one.

The three milestones since — errors and unwinding, macros, collections — found three more. None of them is a dead test, and two of them a mutation check could not have answered at all.

Round five · milestone 4

A defect nothing could observe

Milestone 4 is try/throw/finally and the handler stack. Unwinding is hand-written here: an explicit frame stack means dropping frames, running pending cleanups exactly once, and resuming — no Rust unwinding involved, because the whole design rests on the Rust stack being empty at every instruction boundary.

Five mutants, predictions first. Four died as expected. The fifth was predicted to survive, and did:

Unwinding drops the frames and keeps their slots

Every test stayed green. Not because the code was untested — because the defect cannot be seen from outside the VM.

The leak is bounded. A call’s argument window sits inside its caller’s frame, so the next call reuses the same slot range and never grows past the deepest point already reached. No high-water mark can move. And no value is ever wrong, because the callee prologue fills everything above its arguments with nil — a line that exists for an entirely different reason, so that a frame’s contents are a function of the call rather than of whatever ran there last.

So the mutant is real — dead values retained for the life of the run, and carried into any snapshot — and unobservable. The first response was a test: a tail loop that throws four frames deep and catches, two hundred times, comparing high-water marks against ten iterations.

The test written to catch it was also dead

It passed under the mutant. Writing a second dead test to cover the first one is the milestone-1 failure repeated deliberately, which is a poor way to spend a budget.

The fix is structural, and it is the previous chapter’s lesson arriving in a new place: make it one mechanism instead of two that have to agree.

;; the only place a frame is released — returning and unwinding share it
fn drop_frame(ex: &mut Execution) -> Frame {
    let f = ex.frames.pop().expect("a frame to drop");
    ex.slots.truncate(f.ret_len);
    f
}

“Unwinding forgets to give the slots back” is no longer expressible as a local change. Writing it means breaking returning too, and that is caught by eight tests.

One more from this round, for its shape. A mutant that stopped merging a displaced cleanup error into the one that replaced it was caught — but not by any assertion about errors. It was caught by a check that the run finishes with an empty handler stack, which exists because dropping a handler pop is the first mutation anyone would try. The assertion was doing work no test about the feature was doing.

Round six · milestone 5

A rule everybody knows and nothing was checking

Milestone 5 is macro expansion, quasiquote, and gensym. Six mutants. Four died as predicted, one refuted a prediction in a useful direction, and one survived the entire suite — seventy-five tests, every golden file byte-identical.

;; the mutant: expand a macro’s arguments before invoking it

(defmacro inner [] :expanded)
(defmacro outer [x] `(quote ~x))
(outer (inner))

;; correct:  (quote (inner))
;; mutant:   (quote :expanded)

A macro receives forms — unevaluated, and unexpanded. It is the most basic rule macros have, it is the first line of every tutorial about them, and nothing in the suite observed it.

The reason: every macro in the test suite used its arguments as code, and for those, expanding early and expanding late produce identical output. Telling the two apart requires a macro that keeps an argument as data — which is a shape nobody writes by accident, and which therefore did not exist in the corpus until a mutant demanded it.

The corpus claimed to cover a case it did not

Another mutant dropped everything after a splice in a template. It should have been caught by the corpus. It was caught by one unit test — because every splice in the corpus happened to be the last item, so an expander that dropped the tail expanded the whole file correctly.

The file carried a comment saying it had “a splice, and a tail the splice does not swallow”. It did not. The comment was written first, by someone who had read the chapter about corpora that look representative rather than distinguish, and never checked against a wrong implementation.

The refutation in the other direction is the pleasant one. A mutant that damaged the origins attached to macro output — the positions that make an error inside a macro point at the call site — was predicted to be invisible to every golden file, on the grounds that origins never appear in printed forms. Wrong: the disassembly prints a source position per instruction, and those come from exactly those origins. The bytecode golden is an origin oracle for expanded code, which is a stronger position than milestone 1 was ever in.

A measurement trap, found the hard way

cargo test stops at the first failing test binary. Two mutants in this round looked far weaker than they were, because the tests that would have killed them lived in a later binary that never ran. Count with --no-fail-fast, or the pass systematically under-reports the coverage it exists to measure.

Round seven · milestone 6

Two questions the instrument cannot answer

Milestone 6 is collections, strings, bytes, equality, and the numeric tower — and the rung the build doc has been promising since the beginning: a test suite written in the language itself, run through the real binary.

It found two bugs on its first run. The first was shallow and mine: a map constructor that kept duplicate keys. The second was neither.

;; two distinct literals, one constant-pool entry
(println -0.0 0.0)

  constants
    k0  -0.0          ;; 0.0 deduplicated into -0.0

;; so, in any chunk that mentioned -0.0 anywhere:
(/ 1.0 0.0)  =>  ##-Inf

The constant pool deduplicated by Rust’s PartialEq, and IEEE says -0.0 == 0.0. So two constants that no program should confuse shared an entry, and a division silently produced negative infinity. That code shipped in milestone 2 and had been live for four milestones. It was unobservable until this one, because until this one the language had no float division and no equality to notice with.

A bug only a different rung could see

No mutant would have found it either, because it was not a wrong line — it was a line that was right until the language grew a way to look at it. What found it was a new kind of oracle sitting at a different altitude.

Constants now compare by bit pattern, which is a third equality distinct from both Rust’s and the language’s: two constants may share an entry only when no program can tell them apart. The language’s own = still says -0.0 equals 0.0, because that is what IEEE says and what Clojure does.

The mutation pass then made the second point on its own. Seven of eight mutants died, and every semantic one — numeric equality crossing types, list-versus-vector equality, map order becoming identity, duplicate keys, the constant-pool rule, conj prepending instead of appending — was caught by the in-language suite and by nothing else. The Rust tests were never going to see them.

The eighth mutant could not die

The decision record for this milestone had a performance argument in it. Collections are flat vectors with copy-on-write: Rc::make_mut mutates when the value is not shared and clones when it is, so — the entry claimed — a fresh accumulator in a loop has one reference and mutates a buffer it already owns. That is the whole answer to the open question about whether the language needs transients.

The mutant: replace Rc::make_mut with an unconditional clone. It survived, and it was always going to survive, because the two are behaviourally identical. A mutation check answers behavioural claims only.

So the pass switched instruments. Prediction, written down first: the refcount at a primitive call is 2 rather than 1, because the collection is live in the caller’s argument window while the primitive holds its own clone — so make_mut copies every time and the win does not exist.

;; instrumented conj, building a five-element vector
conj: strong=1 copied=true
conj: strong=1 copied=true
conj: strong=1 copied=true
conj: strong=1 copied=true
conj: strong=1 copied=true

Confirmed, and worse than predicted. It is not only the argument window: in a loop the accumulator is also still bound to a live local until the tail call replaces it. Even nested construction copies, because the inner result sits in a slot and the primitive clones out of it. The transient win is not there at all.

Ten minutes falsified a committed, reviewed paragraph

The decision stands — flat vectors with copy-on-write is still the right shape, and make_mut is still how you write it. What was wrong is the reason, and the reason is the thing that gets reused. Getting the win needs the compiler to kill a slot on its last use, or a call protocol where a primitive consumes its arguments. Neither is a collections question.

That correction went into the errata rather than over the original text. The log is append-only: a wrong reason that reached the right conclusion is worth fixing precisely because someone will reason from it again.

What it adds up to

Seven rounds, six kinds of failure

The first three kinds were about tests. These three are about the apparatus around them:

  • A defect with no observable. Real, and invisible to every value, every golden, and every high-water mark. A test cannot be written for it — the honest response is to remove the way to write the bug.
  • A rule so basic nobody encoded it. Not missed through carelessness: the ordinary uses of the feature cannot distinguish it, so only a shape nobody writes by accident separates right from wrong.
  • A claim that is not behavioural. Mutation is structurally incapable here. The instrument is a number, and the discipline is the same one — write the prediction down first.

The other thing seven rounds shows is that what catches a bug is rarely the rung you would have guessed. Origin damage in macro output was caught by the bytecode disassembly. A displaced-error bug was caught by an assertion about handler-stack depth. A four-milestone-old miscompilation in the compiler was caught by a test suite written in the language, which exists to test the language and not the compiler. Rungs at different altitudes see different things, and the overlap is where the confidence actually comes from.

Knowing about a failure mode still does not prevent it

Chapter one opened with that, about a sibling project’s mutant being reproduced in milestone 1 after being written down as a warning. It happened twice more. The undistinguishing-corpus lesson recurred in milestone 5, in a file whose comment cited it. And the procedural scar — never fix anything while a mutant is applied, because git checkout reverts both — recurred in milestone 4 in a new form: the checkout ate an uncommitted refactor instead. The rule was not about fixes. It is that git checkout does not know which of your changes was the mutant.

Where it stands

Six milestones in

The pipeline has no holes left. Read, expand, compile, run — the smoke script exits 0 for the first time, and the “not built yet” exit code that let it report a pending stage was deleted along with the last gap, because an unreachable branch is one nobody tests.

Every corpus program now carries five snapshots: the forms it reads to, those forms with their span origins, the forms after macro expansion, the bytecode, and — for the ones that run to a defined end, including the ones that fail — a transcript. A failure is a pinnable artifact now, which took deciding what an error is: a thrown value is any value, and a VM-raised fault is a throw with a fixed shape, so try protects against an arity error exactly as it protects against a throw.

Macros are real in the sense that matters: defmacro is not a form the expander knows. It is a macro, written in the language, in a twenty-line prelude compiled into the binary, over the one primitive the expander does know. And the gensym counter it shares with user code turns out to be load-bearing for hygiene rather than incidental — reset it between the prelude and your file, and the prelude’s or would capture a template that binds the same generated name.

What is still not proven is the thing the whole design is for. The execution state is plain data so that a running computation can be suspended, serialized, moved, and resumed — and that claim gets its oracle at milestone 8: run to fuel exhaustion, snapshot, resume in a fresh VM, compare the entire transcript against an uninterrupted run, emitted effects included.

Chapter one ended on that sentence too. It is still the most important property in the project and still an aspiration rather than a fact, which is the only honest way to describe an untested claim — and is, more or less, the point of everything above.
