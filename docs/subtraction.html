A seam nothing compiles is a seam nobody can trust

apolisp has four Cargo features and no users, which means the features are not for turning anything on. They exist so a host capability can be cut out and the language found untouched — and the claim only stays true because a command builds and tests four points of the feature lattice. The two in the middle are the ones carrying the argument.

just subtract/4 features/4 build points/6 cargo invocations/ADR-013

--no-default-featuresNo filesystem, no sockets, no terminal, no JSON. Still a Lisp: closures, macros, exceptions, tail calls.
--features fsFiles and nothing else. Compiles the Host::File variant through one of its two owners.
--features termA terminal and no filesystem. The only build that reaches the other owner.
defaultAll four, which is what just verify already runs. Free, and proves nothing on its own.
The rule

Seams exist for subtraction, not for organisation

The project’s ethos file states the boundary rule in a way that rules out most of the reasons people draw boundaries:

A boundary earns its place when a subsystem can be deleted or lifted out. That is a different driver from modularity, and it is the one that applies here: needing a home for code is not a reason. The test is mechanical — cut the subsystem out and see whether it still builds.

Which raises the obvious question about a claim like that: who ever runs the cut? A seam described in a design document and never compiled without its other half is a seam that has already rotted, and nothing will say so. So the features exist to run it. ADR-013 is explicit that they are a harness and not a product surface:

The features are not there for users — there are none. They are the subtraction test harness: building with a host adapter cut out is how “seams exist for subtraction” stays a fact rather than a feeling.

The same entry draws the line that keeps this from becoming a configuration matrix. Features gate host capability — filesystem, sockets, terminal, JSON. They never gate macros, metadata, or exceptions. Feature-gating core semantics turns one system into 2n systems, which is a direct assault on the constraint everything else defers to: the whole core has to be holdable in one reading. The VM knows exactly one generic HostCall opcode, so which host functions exist is a registry question rather than a compilation question.

What a cut removes

One capability, one edge

An adapter’s entire attachment to the VM is one line in one function. The comment above it is the design constraint stated as a fact about the code:

/// Every adapter enabled in this build. The single edge each one has on the
/// VM: cut the module and the matching line here is all that stops compiling.
pub fn install(vm: &mut Vm) {
    #[cfg(feature = "tcp")]
    tcp::install(vm);
    #[cfg(feature = "term")]
    term::install(vm);
    #[cfg(feature = "json")]
    json::install(vm);
    let _ = vm;
}

Below that, a capability owns a variant of the live-resource enum, and cutting the feature takes the variant, the primitives that construct it, and every arm that reads it. Nothing in the VM changes. That is the shape the whole arrangement is trying to preserve, and it is why the enum carries its own note about it:

pub enum Host {
    /// ADR-013's subtraction harness, and the first place it is real: build
    /// without `fs` *or* `term` and this variant, the primitives that
    /// construct it, and the three arms that read it all go.
    #[cfg(any(feature = "fs", feature = "term"))]
    File(std::fs::File),
    Stdin,
    Stdout,
    #[cfg(feature = "tcp")]
    Tcp(std::net::TcpStream),
    #[cfg(feature = "tcp")]
    Listener(std::net::TcpListener),
}

Stdout has no gate because it is not a descriptor. It is the buffered in-memory host: a write goes into a buffer the snapshot serializes, not out to the process. With fs, tcp and term all cut, nothing in that module writes to the outside world at all — which is the subtraction working rather than a special case for it.

The lattice · why the command is six invocations and not two

Four points, and the two that carry the argument

Four features is sixteen possible builds. The harness builds four of them, and the choice is the interesting part — because the two obvious ones, everything on and everything off, cannot tell the two most likely #[cfg] mistakes apart.

Host::File is gated any(feature = "fs", feature = "term"). Suppose someone writes all instead, or narrows it back to fs alone. Here is what each build point observes:

Buildany(fs, term)all(fs, term)Can the endpoints tell?
--no-default-featuresabsentabsentNo — both gates agree
--features fspresentabsentYes — the gates disagree here
--features termpresentabsentYes — and only here for term
default (all four)presentpresentNo — both gates agree

With only the endpoints, any(a, b) and all(a, b) are indistinguishable. Every build is either green or red for both, so a gate written as if two capabilities always travel together compiles everywhere and is wrong nowhere anything looks. The middle points are the entire test. The justfile says so where someone changing the recipe will read it:

# Four points, not the whole 2^4 lattice: everything off, `fs` alone, and `term`
# alone. The middle points are the ones that catch a `#[cfg]` written as if two
# features always travel together — with only all-on and all-off, `any(a, b)`
# and `all(a, b)` are indistinguishable.
subtract:
    cargo clippy --no-default-features --all-targets -- -D warnings
    cargo test   --no-default-features
    cargo clippy --no-default-features --features fs --all-targets -- -D warnings
    cargo test   --no-default-features --features fs
    cargo clippy --no-default-features --features term --all-targets -- -D warnings
    cargo test   --no-default-features --features term

The term-alone point is younger than the others, and it exists because of a bug the earlier lattice could not have

Until ADR-051, Host::File was gated on fs alone, and the only way to paint a terminal was (io/open "/dev/tty" :write) — which is the filesystem capability. So a build with term and without fs could read keystrokes and could not draw anything. A half-present capability, in a build nothing compiled and no test ran.

ADR-051 made a tty a handle like any other, so painting is io/write to it, so Host::File now has two owners and a term-only build has to compile that arm. The lattice gained a point that means something, and the decision record accounts for the cost honestly: one more #[cfg] naming two features is one more place to be wrong, mitigated by the new point failing to compile if the gate ever narrows again.

The gate was checked by breaking it

The claim “this point fails to compile if the gate narrows” is not left as an argument. ADR-051 records it as verified by reverting the widened #[cfg] and counting what happened: six errors in the term-only build. A new check believed without being broken first is the project’s most reliable source of checks that test nothing.

Why it runs the tests

Compiling proves the gates line up. Running proves the language is still there.

The recipe is a full cargo test at each point rather than a cargo check, and the difference is the actual claim. Compiling shows the #[cfg]s are consistent. It says nothing about what a program sees when a capability is gone — and what it should see is the least dramatic thing available:

(try (io/open "x") (catch e (get e :kind)))
;; in a build without `fs`:  :unbound

Not a parse error, not a different dialect, not a special “capability missing” fault. An ordinary unbound global, exactly like a name nobody defined. Two tests hold that down, and both are written so a single file states the whole matrix and each build checks its own row:

  • A feature removes its primitives and nothing else. Every assertion is a cfg!: is_bound("io/open") must equal cfg!(feature = "fs"), and so on for all four. Then a list that must be bound in every build — +, count, conj, str, println, gensym, io/stdout — plus a closure and a try/catch that must still evaluate. That second half is ADR-013’s no-2n-languages clause, as an assertion.
  • A cut capability is an ordinary unbound global. It loops over the capabilities that are absent from this build and checks each raises :unbound.

The second one has a detail worth copying. In the default build every capability is present, so its loop body never runs and the test asserts nothing at all. Rather than let it read as coverage, it says so:

if !any {
    eprintln!("all capabilities present; this test asserts nothing in the default build");
}

A test that is vacuous in the build most people run is not a bug — the matrix is what makes it non-vacuous elsewhere. It is a bug only if nobody can tell.

The limit

It proves a capability can be removed. It cannot notice a semantic left with it.

Ten milestones in, someone wrote an ordinary program — not a test — and found that the language had no way to turn a string into a number. Not an awkward way. None. The primitive table converted values to strings and never back, so a length header, a config value, a line of user input were all unreachable.

The one path that worked was (json/decode "27"). And json is an optional host adapter, which makes the consequence worse than the gap:

The subtraction build was green the whole time

--no-default-features removed the language’s only way to read a number out of text. ADR-013 says features gate host capability and never language semantics, and that had quietly stopped being true — not because a feature gated a semantic, but because a semantic had no home and was squatting in a feature.

The harness could not catch it and still cannot catch its like. The build without json passed because nothing in the test suite parses a number from a string either. The subtraction harness proves a capability can be removed; it cannot notice that a semantic went missing with it.

The repair (ADR-046) made parse-number a core primitive, unconditional in every build, and made it be the reader’s own number grammar rather than a second implementation — so a literal and a parsed string cannot drift. Which surfaced a smaller bug immediately: the non-finite spellings had been three arms of the reader’s token match sitting in front of the shared function, so (parse-number "##Inf") answered nil while the reader read the same characters as a float. A shared grammar the caller can add cases in front of is not shared.

The finding worth keeping is the shape of the blind spot rather than the bug. A subtraction test asks “does this still build and pass with X gone?” It can only ever be as strong as what the suite would miss X for. The thing that found this was a person writing a program that had to read a number, which is a category of oracle no amount of strengthening the harness produces.

Where it stands

The cost, which is the honest part

16possible builds
4built and tested

The adapters sit outside the line budget on purpose, because substantial host capability is a Rust library behind the handle table rather than a language subsystem. That exclusion is drawn by path in the budget test and it prints every excluded file with its count, so moving lines out of the budget by moving them into adapters/ is visible rather than quiet.

What the arrangement buys is narrow and worth stating plainly: a minimum binary carries the full language even when an application uses almost none of it. That is the accepted cost, on the grounds that the language is the small part. And the terminal half has no Windows story — /dev/tty is Unix, and the decision record says so rather than implying portability it does not have.
