The program

The most ordinary interactive program there is

The ethos names three target workloads — terminal applications, web services, simulators. Two earlier programs had covered a simulator and a service, so the terminal was the one left. It is also where the least-exercised code in the repository lives: term.rs is 120 lines behind three natives, and the whole suite’s coverage of it is one arity check.

So: a pager. Show one screenful of a file, scroll with j/k/space, quit with q. Chosen for being unremarkable.

It works, and the first version of it cannot work. The gap between those two sentences is the finding.

Written first

Five predictions, and the one that was not a wish list

Filed before running anything, in the habit the project asks for. Four held and were minor. The fifth held and was the whole result.

Held

No ESC literal — the reader takes \n \t \r \\ \" and nothing else.

Held

No cursor or clear natives; the adapter abstracts input and not output.

Held

Raw mode has no scope form, so try/finally has to carry it — and will.

The one

io/stdout is buffered until the program ends, which would make an interactive program unwritable.

Moot

No mod, only rem. Irrelevant here — a pager clamps rather than wraps.

Worth flagging against the other pre-registrations

Three rounds of prediction elsewhere in this project all had their largest finding absent from their own list. This one predicted its headline. The difference is what was being predicted: buffering was a known mechanism whose consequence had never been faced, not a cost nothing could yet measure. Predicting the consequence of something you already understand is a much easier trick, and the note says so rather than claiming a hit.

Measured, not read

Two writes twenty-four seconds apart, arriving together

io/write to io/stdout calls vm.emit, which appends to vm.out. The driver prints that buffer after the run returns, under a --- stdout header. Nothing reaches the process’s real stdout while the program is running.

056.177  --- stdout
056.213  first      ← 24 seconds of work separates these two writes
056.246  second     ← they arrive 33 ms apart

For a batch program that is invisible. For a terminal program it is fatal, and the way it fails is worth seeing. Driven under a real pty, fed j j space k q at 0.6-second intervals:

  0.63  KEY  'j'
  1.27  KEY  'j'
  2.00  KEY  ' '
  2.65  KEY  'k'
  3.37  KEY  'q'
  3.37  OUT  223b  '--- stdout\r\n<ESC>[2J<ESC>[H ... 1/61 ... 2/61 ...'

Five keystrokes against a blank screen, and then all five frames painted at once, into a terminal that has already stopped caring. term/read-key blocks live on the real tty, waiting for a keystroke the user was never shown a prompt for — because the prompt is still in a buffer.

The program itself is correct. The frames say 1, 2, 3, 12, 11, which is exactly what j j space k should do against a ten-row window; raw mode is restored; it exits 0. Correctness was never the problem.

The shape of it

Two subsystems, each right on its own

Input

term/read-key reads the real tty, immediately, blocking. Correct, and exactly what an event loop needs.

Output

io/write appends to a buffer the VM owns and the driver flushes at exit. Correct, and load-bearing for something else entirely.

This is not a missing feature in term.rs. Both halves were built deliberately, both are right in isolation, and they had never been in the same program before. A test suite could not have found it: the input half has one arity check, the output half is asserted by every golden transcript in the corpus, and nothing had ever needed them to agree about when.

The line endings are wrong for the same reason

The pager writes \r\n, which is correct under raw mode. The captured bytes are \r\r\n. The buffer is flushed after the finally has already turned raw mode off, so the tty applies ONLCR to a newline that was never supposed to get it.

A program cannot write correct bytes for a terminal mode it is guaranteed not to be in when the bytes are sent.

The workaround

Two lines, and a capability that turns out to be half present

io/write takes a different path for a file than for stdout — files get write_all on the real descriptor, and only stdout goes through the buffer. So opening the terminal as a file bypasses the buffer entirely:

(def tty (io/open "/dev/tty" :write))
(def out (fn out [s] (io/write tty s)))

Two lines, and the same pager becomes a real application:

  0.01  OUT      7b  '<ESC>[2J<ESC>[H'      ← paints before it blocks
  0.01  OUT    350b  '; A full-screen pager. Show one screenful ...'
  0.67  KEY  'j'
  0.68  OUT      7b  '<ESC>[2J<ESC>[H'      ← ~10 ms later
  0.68  OUT    329b  '; quit with q. It pages its own source ...'

It paints before it blocks, responds in about ten milliseconds, scrolls, clips to the window width, restores the terminal on q, and the line endings are now \r\n because raw mode is genuinely in effect when the bytes go out.

And the cost, which is the second finding

/dev/tty is io/open, which is the fs feature. So a build with term and without fs is a terminal you can read keys from and cannot paint to — a capability half present, with nothing saying so.

The subtraction harness could not see it. Its three build points at the time were everything off, everything on, and fs alone, so term without fs was never built — and no test paints anything in any configuration anyway. This was the third instance of that one pattern, which is the count at which it stopped reading as an accident: the first was the language’s only string→number path living inside the JSON adapter, so that turning JSON off removed a semantic.

The tension

The buffer is not an accident to be removed

The obvious fix — make io/stdout unbuffered — would break the thing the buffer exists for. The buffered host is the oracle for the project’s second governing constraint: emitted effects are part of the serialization round-trip comparison rather than escaping it, and that property is the only reason “a running computation can be suspended, moved, and resumed” is a property instead of an aspiration.

/dev/tty escapes it. Which put the project in an awkward position and the note recorded it as such rather than resolving it:

A program written the only way a terminal program can currently be written is a program whose output the round-trip property cannot see — so the terminal workload and constraint #2 do not currently meet anywhere.

Filed as an open question rather than fixed, because it is a decision and not a bug.

The resolution

The refusal turned out to be the design

The entry that settled it inverted the reading. The snapshot serializes the output buffer, which means buffered output is resumable machine state, not a test fixture. So the invariant that has to hold is not “a terminal program should be snapshottable” but its opposite:

If output escaped the buffer, refuse the snapshot.

Painting now goes through a handle — (term/open) returns one on /dev/tty, and io/write to it is the same primitive a file and a socket use. A live handle is not reconstructible, so the existing rule already makes a snapshot refuse while one is open. No new code, no new decision, and the handle table enforces the invariant without anyone having to remember it. Every other shape would have to re-derive the refusal by hand.

A painting program being non-snapshottable is therefore the design, rather than the concession it reads as above. And the half-present capability got closed in the same entry: a tty became any(fs, term) rather than fs, and the subtraction harness gained term alone as a fourth lattice point — the build that had been unreachable is now one of the four that has to compile and run.

What the program was actually for

None of this is a defect the pager exposed in the language. It is a decision the language had not been asked to make, because nothing had ever put the two halves in the same room — and the shape of the answer came from having a broken program in front of it rather than from arguing about buffering in the abstract.

What held

A loop inside a try, measured rather than assumed

One thing is worth recording because the rules make you expect the opposite. A call in tail position inside try/finally is not a tail call here — the cleanup still has to run. A terminal event loop is always inside a try, since that is the only way raw mode gets restored. If recur inherited that rule, every terminal program in this language would have a bounded lifetime.

It does not. And this was measured rather than reasoned about, because a heap-allocated frame that grows would not announce itself by overflowing:

Iterations inside a tryPeak RSS
100,0003.42 MB
1,000,0003.39 MB

Ten times the work, no growth. recur is a jump within the frame and never touches the handler stack. That is the kind of claim that is cheap to assume and cheap to check, and the gap between those two costs is the entire argument for checking it.

And the library carried the program

split, take, drop, map, join, str-scalar-len — nothing was hand-rolled, the first time that had been true. The clamping behaviour of take and drop turned out to be exactly right for scrolling: dropping past the end of a buffer is an empty page rather than an error, so the clamp at the top of the loop is the only bounds logic in the program.

Which is the trajectory in the header, stated as a ratio. Six of seventeen definitions, then thirty of fifty-four lines, then four of forty-six — and those last four are not missing functions. They are an ESC constant, a clear sequence, a handle, and a one-line out.

The gaps have moved off the language surface and onto the host boundary.

Three programs, three rounds, and each round’s gaps were invisible until the previous round’s were fixed — iteration hid strings, strings hid ordering, and all of them together hid the fact that nothing had ever painted anything. It is the same shape as a benchmark on a system with one dominant quadratic: what you can see is bounded by what you have already removed.
